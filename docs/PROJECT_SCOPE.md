# 项目范围：固定训练任务上的搜索过程自适应

## 一、最终问题

在每个候选的每个训练 seed 使用 **1 张 H200、约 10 分钟训练**的条件下，研究实验反馈能否通过更新 harness 的记忆组织、流程结构和探索前沿，提高寻找优质小型语言模型的效率。模型参数自进化作为下一阶段：代码先准备，待用户有算力后运行。

具体方法、三组件状态定义和可检验假设见 [HARNESS_EVOLUTION.md](HARNESS_EVOLUTION.md)。

项目分为两个独立对象：

1. **被搜索的模型配置 c。** 每个配置对应一次从头训练、量化保存、重新加载和验证。不同配置形成实测 lookup table。
2. **搜索系统的状态。** 系统依据已观察到的配置与验证分数决定下一次查询。harness、agent 群体和策略权重分别构成三类可更新状态。

普通进化搜索会改变 c；本项目的核心比较则是“允许保留搜索系统的更新”与“同样获得反馈、但冻结对应状态”的差异。更新机制本身仍由预先编写的代码确定，因此目前研究的是系统自适应，不把它直接表述为改进更新器自身的递归元学习。

## 二、可完成的课程项目范围

### 任务

- 固定一台、一个具体型号的 H200 和软件环境。
- 24 个预注册设计配置，每个配置训练 seeds 0、1、2。
- 每次训练目标 600 秒，完成当前训练步后停止；实际用时全额记录。
- 以压缩模型重新加载后的搜索验证 BPB 为目标，越低越好。
- 模型压缩文件加独立运行源码不超过 16,000,000 字节。
- 固定官方 SentencePiece 1024 tokenizer、训练数据前缀、评估上下文和量化方法。
- 官方 validation 按完整文档边界预先分成 search/confirm；搜索期间不使用 confirm 分数。

### 方法

七个默认条件：随机搜索、regularized evolution、memory/structure/frontier 全部自适应、全部冻结，以及分别冻结一个组件的三项消融。每个 search seed 的四个起始配置一致，且计入预算。三个 single-only 条件可进一步补齐 2³ 全因子设计；加上两个基线共十个条件，用于估计平均主效应与交互。

先前的四参数 harness、multiagent 和 weight 对照仍保留为显式可选方法，已有 CPU 结果归档。默认研究集中于新的 harness 方向。

默认 harness 是显式本地策略。权重策略同时提供 NumPy 实现和可选的真实 HuggingFace causal LM LoRA 实现；后者需要用户提供本地预训练权重。它采用只允许合法标签的 action distribution，并用已评估验证收益更新 adapter。本阶段不运行预训练控制模型的参数更新实验。

### 交付

训练入口、固定任务清单、实测结果协议、完整性检查、回放实验、配对统计、winner 锁定、隐藏文本确认、可恢复记录以及课程汇报可直接引用的结果报告。

## 三、默认设计空间

| 因素 | 取值 | 解释 |
| --- | --- | --- |
| 层数 | 4 / 6 / 8 | 改变深度和每 token 计算量 |
| 宽度 | 256 / 384 | 改变表示容量与吞吐；heads 根据宽度确定 |
| 输入输出 embedding 共享 | 是 / 否 | 改变参数利用和最终压缩大小 |
| 全部学习率组的倍率 | 0.7 / 1.3 | 保持优化器类型，改变训练更新尺度 |

共 3×2×2×2=24 个配置。宽度对应 `num_heads=width/64`、`num_kv_heads=width/128`。模型邻域的距离只计算四个独立因素，不把派生 head 数重复算成多个变动。

固定 global batch 为 524,288 tokens，序列长度 1024；单卡八次累积，对应 microbatch 64。该选择沿用 pinned baseline 的 batch 定义，并非完成过 H200 性能调优的结论。若首个正式任务 OOM 或吞吐异常，应在整表测量前修订配方并生成新的 space/manifest，而不是逐候选偷偷改变 batch。

## 四、预算

默认建表：24 配置 × 3 训练 seed × 10 分钟 = **12 个训练 GPU 小时**。

搜索回放不重新训练这些模型。它计算两种成本：实际支付的建表成本，以及假设搜索在线调用这些候选时会花费的虚拟训练成本。两者分别报告，不把 480 次 CPU 回放说成又进行了 480 次 GPU 搜索实验。

一次配置查询读取三个训练 seed 的均值，因此对应约 30 个训练 GPU 分钟。12 次配置查询对应约 6 个训练 GPU 小时的在线模拟预算；每个底层训练 job 仍是单卡约十分钟。

最终确认只对所有锁定结果中的去重配置运行新训练 seeds 100、101、102。若共选出 K 个不同配置，确认额外需要约 K/2 个训练 GPU 小时。K 在搜索结束后确定，确认成本不能混入原先的 12 小时。

原先 A100/H100 双表与默认 1 小时校准方案已经退出默认计划。可选 600/3600 秒代理排序分析工具保留，但不是用户此次 H200 10 分钟要求的必跑项。

## 五、可以提出的研究结论

H200 数据完成后，可检验：

1. 在相同查询预算下，adaptive 比对应 frozen 是否获得更低的最佳验证 BPB？
2. 在相同实测候选训练成本上限下，差异是否仍存在？
3. 系统实际保留了哪些记忆组织、执行图和前沿策略更新，更新何时影响了后续候选？
4. 锁定配置在新训练 seed 和隐藏确认文本上是否维持质量？

配对差值、置信区间、胜/平/负和失败率共同构成证据。即使结果为零或负，也能形成有效结论：在这个任务和预算内，额外自适应是否值得其成本。

同时记录整个搜索过程的 incumbent regret：固定查询时对共同初始化之后的查询前缀取均值；固定成本时对已有 incumbent 的 regret 随累计成本积分。全因子分析分别报告平均主效应与交互，不把“全开减去冻结一项”直接当成独立主效应。

24 个配置是机制验证与初步比较的规模。若多个方法很快达到同一个表内最优点，应报告饱和，并在下一版预注册更大或新的任务空间。不能事后只挑有利 budget 或 seed 宣称提升。

## 六、当前结果能说明什么

已经完成的是 authored text fixture 上的 CPU 链路验证：真正训练、真正量化往返、真正读取实测表、配对搜索和隐藏文本确认。它确认实现能够记录真实更新，也能报告负结果。

这些数值不支持 H200 加速、FineWeb 提升、预训练 LLM agent 能力或跨任务泛化的结论。H200 实验按用户要求交由用户运行；所需代码与固定任务清单已准备。
